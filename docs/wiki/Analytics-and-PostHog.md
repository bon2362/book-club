# Аналитика и PostHog

PostHog используется для продуктовой аналитики: кто пришёл, что делал, до какого шага дошёл,
где прервался, были ли ошибки. Он подключается и на клиенте (в браузере), и на сервере, и уважает
Do Not Track.

## Что собирается

| Что | Откуда | Комментарий |
| --- | --- | --- |
| Внутренний идентификатор пользователя (UUID) | клиент | Ставится после входа через `identify(userId)`. До входа посетитель анонимный, person profile не создаётся. |
| Имя и telegram-username | сервер | Свойства профиля (person properties), ставятся сервером в момент успешного входа. Не идут через браузер. |
| Email | — | **Осознанно не передаётся.** Решение владельца проекта — аналитика не должна давать прямой канал связи с человеком. |
| Просмотры страниц, клики | клиент | Autocapture — знает текст кнопки и адрес страницы, но не знает бизнес-смысл (например, какую книгу разворачивали). |
| События входа, дублей аккаунтов, работы с книгами | клиент и сервер | См. таблицу событий ниже. |
| JavaScript-ошибки на странице | клиент | Автоматический сбор (`capture_exceptions` в `posthog.init`). Отвечает на вопрос «были ли у пользователя проблемы» без записи экрана. |
| Общая информация о браузере/устройстве | клиент | Тип устройства, ОС, страна по IP — стандартный сбор PostHog. |

**Запись экрана (session replay) не включена** — решение владельца, слишком чувствительно к приватности.

Если `NEXT_PUBLIC_DISABLE_ANALYTICS=true`, аналитика отключается на клиенте.

## Тестовый режим: аналитика полностью выключена

Когда `NEXTAUTH_TEST_MODE=true` (так работают тестовые прогоны, включая ночные E2E),
серверная отправка событий — no-op: события не долетают до PostHog вообще. Это защищает
боевой проект PostHog от того, чтобы E2E-прогоны заливали в него мусорные события и портили
воронки и дашборды. Тот же no-op срабатывает, если `NEXT_PUBLIC_DISABLE_ANALYTICS=true` или
серверный токен PostHog не задан.

## Таблица событий

| Событие | На какой вопрос отвечает | Клиент / сервер |
| --- | --- | --- |
| `auth_modal_opened` | Открыл ли посетитель модалку входа | клиент |
| `auth_attempt` | Какой способ входа выбрал и откуда (`entry_point`: header / book_signup / submit_book) | клиент |
| `auth_email_link_sent` | Отправлена ли ссылка для входа по почте | клиент |
| `auth_error_shown` | Вход не удался и человек увидел ошибку — чаще всего протухшая ссылка из письма (`Verification`). Разрыв между «письмо отправлено» и входом объясняется этим событием. | клиент |
| `auth_succeeded` | Вход завершился успешно; новый пользователь или нет, как он был опознан (`provider`, `is_new_user`, `linked_by`) | сервер |
| `auth_failed` | Вход не удался и почему (`provider`, `reason`) | сервер |
| `auth_abandoned` | Пользователь закрыл модалку входа, не завершив вход | клиент |
| `account_duplicate_suspected` | Похоже, в этом браузере только что создался второй аккаунт вместо входа в существующий | клиент |
| `identity_conflict` | Попытка привязать способ входа, который уже занят другим аккаунтом | сервер |
| `accounts_merged` | Администратор слил два аккаунта в один | сервер |

### Выбор книг и интерес к проекту

| Событие | На какой вопрос отвечает | Клиент / сервер |
| --- | --- | --- |
| `book_card_expanded` | Какую книгу человек захотел прочитать подробнее: `book_id`, `book_title`, `tags`, `position` (место в списке), `is_mobile`. Шлётся только на разворачивание описания, не на сворачивание | клиент |
| `book_text_opened` | Ушёл читать сам текст книги | клиент |
| `book_summaries_opened` | Пошёл смотреть саммари клуба по книге | клиент |
| `book_signup` / `book_unsignup` | Записался на книгу или снял запись. Кроме id и названия: `tags`, `position` и `expanded_before` — читал ли человек описание перед записью | клиент |
| `about_section_opened` | Какой раздел «о проекте» раскрыл («Для кого это?», «Чем это не является?» и т. п.) | клиент |
| `timeline_opened` | Открыл ленту времени | клиент |
| `summaries_opened` | Открыл страницу саммари книги | клиент |
| `priorities_updated` | Расставил приоритеты книг (`count` — сколько книг в списке) | сервер |
| `calendar_slots_marked` | Отметил своё свободное время (`slot_count`) | сервер |
| `circle_meeting_scheduled` | Встреча круга назначена (`circle_id`, сколько участников отметилось) | сервер |

Как этим пользоваться:

- **«Читают ли описание перед записью»** — свойство `expanded_before` у `book_signup`. Если
  большинство записей приходит с `false`, люди выбирают по обложке и названию, а описание не работает.
- **«Какие темы притягивают»** — свойство `tags` у `book_card_expanded` и `book_signup`. Теги уходят
  списком, поэтому в PostHog по ним можно фильтровать как по значениям, а не искать подстроку.
- **«Где интерес упирается в вход»** — `book_card_expanded` → `auth_modal_opened` с
  `trigger = book_signup` → `auth_succeeded` → `book_signup`.
- **Воронка доведения до конца:** `book_signup` → `priorities_updated` → `calendar_slots_marked`
  → `circle_meeting_scheduled`.

Отметки свободного времени не привязаны к кругу: в этом проекте свободное время хранится
глобально у пользователя, а страница календаря — на круг (см. `docs/features/calendar.md`).
Поэтому у `calendar_slots_marked` нет идентификатора круга, и это не упущение.

### Каталог, профиль и навигация

| Событие | На какой вопрос отвечает | Клиент / сервер |
| --- | --- | --- |
| `catalog_filter_changed` | Каким фильтром пользуются и сколько книг осталось: `filter` (`tag`, `author`, `new`, `my_books`, `read`), `value`, `results_count`. Сброс фильтра — `value = все` | клиент |
| `catalog_searched` | Что ищут в каталоге: `query`, `query_length`, `results_count`. Одно событие после паузы в наборе, а не на каждую букву. `results_count = 0` — книги, которых не хватает | клиент |
| `catalog_view_changed` | Переключают ли вид каталога (`mode`: `grid` / `list`) | клиент |
| `submit_book_clicked` | Откуда предлагают книги: `entry_point` (`header`, `catalog_card`, `catalog_table`), `is_logged_in` | клиент |
| `about_block_expanded` / `about_block_collapsed` | Раскрывают ли блок «Что это» (`source`: клик по блоку или кнопка «Подробнее») | клиент |
| `about_block_closed` | Закрыли блок крестиком; `was_expanded` — читали ли перед этим | клиент |
| `matching_strip_clicked` / `matching_strip_dismissed` | Полоса «Идёт матчинг» на главной: перешли в матчинг или закрыли | клиент |
| `profile_opened` | Открыли личный кабинет (`source`: `header` — имя в шапке, `priority_hint` — подсказка о приоритетах) | клиент |
| `profile_tab_opened` | Какие вкладки кабинета смотрят (`tab`: `signup`, `submitted`, `profile`) | клиент |
| `profile_book_clicked` | Нажали на книгу в кабинете — открывается меню статуса | клиент |
| `profile_book_removed` / `profile_book_restored` | Убрали книгу из списка или вернули | клиент |
| `profile_books_reordered` | Перетащили книгу — расставляют приоритеты руками: откуда, куда, сколько книг в списке | клиент |
| `profile_book_status_changed` | Сменили статус книги (`from` / `to`: `want_to_read`, `reading`, `read`) | клиент |
| `profile_language_toggled` | Отметили или сняли язык чтения | клиент |
| `profile_identity_link_started` / `profile_identity_linked` / `profile_identity_link_failed` | Привязка способа входа в кабинете: начали, получилось, не получилось и почему (`provider`, `reason`) | клиент |
| `profile_identity_link_email_sent` | Отправлено письмо для привязки почты — привязка завершится, когда человек откроет ссылку | клиент |
| `account_deletion_cancelled` | Нажали «Удалить аккаунт» и передумали | клиент |
| `calendar_timezone_changed` | Сменили или подтвердили часовой пояс в календаре круга | клиент |

**Почему нет события «аккаунт удалён».** При удалении аккаунта сайт стирает профиль в PostHog вместе со
всеми его событиями — это право на забвение из политики приватности. Событие об удалении исчезло бы вместе с
остальными, поэтому пишутся только передумавшие. Сколько людей удалило аккаунт, видно в нашей базе, а не в PostHog.

**Глубина прокрутки** отдельным событием не отправляется: PostHog сам записывает её при уходе со страницы
(свойство `$prev_pageview_max_scroll_percentage` у события `$pageleave`). По ней видно, до какого места
люди долистывают каталог.

**Автозахват кликов** включён и пишет все нажатия, но значение полей (что выбрали в фильтре, что ввели в поиск)
PostHog намеренно скрывает. Поэтому для фильтров и поиска заведены отдельные события выше.

Воронка входа: `auth_modal_opened` → `auth_attempt` → (для почты: `auth_email_link_sent`) → `auth_succeeded`.

Свойство `linked_by` у `auth_succeeded` говорит, как система опознала человека: `identity` — по уже
привязанному способу входа, `email` — склеили по почте, `new` — аккаунт создан этим входом,
`adapter` — вход через Google или ссылку из письма, где пользователя находит или создаёт адаптер
NextAuth. Путь `adapter` долгое время не отправлял ни события, ни имени: в PostHog эти два способа
выглядели как «ими никто не входит», а вошедшие оставались безымянными. Если такое повторится,
проверять надо колбэк `signIn` в `lib/auth.ts` — свойства персоны для этого пути ставятся там,
а не в `resolveOrCreateUserFromIdentity`.

Имя и никнейм проставляются **только в момент входа**. У человека с живой сессией (она держится
неделями) в PostHog может не быть имени, пока он не войдёт заново, — это не поломка.
Успешный переход по ссылке из письма отдельным событием не отмечается — он и есть `auth_succeeded` с `provider = email`. Люди, отвалившиеся между отправкой письма и входом, видны как разрыв в этой воронке, а причина — в `auth_error_shown`.

Механика `account_duplicate_suspected`: в базе нет технического способа склеить Telegram-аккаунт
с email-аккаунтом без email — то есть «вошёл через Telegram, потом через Google» технически
выглядит как два разных человека. Браузер запоминает последний известный внутренний
идентификатор; если сайт распознаёт пользователя под другим идентификатором в том же браузере —
это сигнал вероятного дубля. Ловит только случай «тот же браузер»; дубль с другого устройства так
не поймать — там нужна сверка в админке.

## Где PostHog встроен в проект

| Часть | Назначение |
| --- | --- |
| `components/PostHogProvider.tsx` | Оборачивает приложение и управляет pageview/identity на клиенте. |
| `lib/analytics.ts` | Клиентские helper-функции PostHog. |
| `lib/posthog-server.ts` | Серверная отправка событий (`captureServerEvent`) и best-effort удаление PostHog person при удалении аккаунта. |
| `/api/admin/posthog-usage` | Админский endpoint для месячного usage. |
| `PostHogUsageWidget` | Виджет в админке: события за месяц и лимит. |

### Серверный слой

Серверные события (успех/неудача входа, конфликт identity, слияние аккаунтов) отправляются не из
браузера, а с сервера — потому что сам факт «человек успешно вошёл» или «система поймала попытку
привязать чужой аккаунт» происходит в серверном коде, а не в интерфейсе. Отправка устроена так,
чтобы ошибка аналитики никогда не ломала обычный запрос пользователя (best-effort, события
собираются в очередь и явно сбрасываются перед завершением ответа — иначе на serverless-функциях
Vercel они могут потеряться).

## Важные переменные

| Переменная | Зачем |
| --- | --- |
| `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN` | Клиентская отправка событий. |
| `NEXT_PUBLIC_POSTHOG_HOST` | Host PostHog, обычно EU. |
| `POSTHOG_PERSONAL_API_KEY` | Server-side API: usage и удаление person. |
| `POSTHOG_PROJECT_ID` | ID проекта для PostHog API. |
| `NEXT_PUBLIC_DISABLE_ANALYTICS` | Отключает аналитику на клиенте. |
| `NEXTAUTH_TEST_MODE` | Когда `true` — серверная отправка событий полностью no-op (тестовый режим, ночные E2E). |

## Приватность

PostHog настроен так, чтобы:

- не создавать person profile для каждого анонимного посетителя;
- уважать Do Not Track;
- идентифицировать пользователя только после входа;
- передавать имя и telegram-username, но не email;
- не включать запись экрана (session replay);
- не запрашивать remote feature flags на клиенте;
- при удалении аккаунта пытаться удалить PostHog person best-effort.

Актуальный публичный текст об этом — `content/privacy.md`, раздел «Какие данные собираются».

## Что проверять

| Симптом | Проверка |
| --- | --- |
| Виджет в админке говорит not configured | `POSTHOG_PERSONAL_API_KEY`, `POSTHOG_PROJECT_ID`. |
| Нет событий | `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN`, host, DNT, блокировщики. |
| События не должны собираться в тестах | `NEXTAUTH_TEST_MODE=true` (серверный слой) и `NEXT_PUBLIC_DISABLE_ANALYTICS=true` (клиент) — оба обязаны быть выставлены в тестовом окружении, иначе ночной E2E зальёт события в боевой проект PostHog. |
| После удаления пользователя остались данные | Проверить PostHog API key scope и manual cleanup. |
