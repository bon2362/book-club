# Matching: «Готов читать 2 книги за раз» (reading capacity 1→2)

**Issue:** https://github.com/bon2362/book-club/issues/195
**Дата:** 2026-07-06
**Статус:** superseded (2026-07-16) — см. ниже

> книжный режим (`docs/planning-artifacts/prd-matching-books.md`, PR #474/#476): сценарная
> вкладка переведена в read-only, модель подтверждений заменена интентами и назначениями.

>

> - продуктовое решение: явный opt-in, дефолт 1, cap 1→2;
> - решение А: нельзя понизить capacity, пока заняты 2 слота — участник сам освобождает один;
> - решение Б: capacity меняет только сам участник (переспросить: в книжном режиме у админа

> - хранение: `reading_capacity` в `matching_session_participants`;
> - метод: найти все места, где вшит «один юзер = один слот». В книжном режиме это
>   PK `matching_book_assignments (session, user)`, уникальный индекс hard-интента,
>   логика формирования/автоназначения и UX «единственный слот занят».
>
> Новую спеку писать после вердикта «книжный vs сценарный» по итогам 1-2 реальных сессий.

## Проблема

Сейчас подбор жёстко предполагает «один участник = один круг = одна книга». Некоторые
участники готовы читать 2 книги параллельно, и страница должна это отражать: сценарий с
несколькими кругами вокруг такого участника может улучшать общий расклад.

## Продуктовое решение

Явный **opt-in**: переключатель «Готов читать 2 книги за раз», по умолчанию **выключен**
(capacity = 1). Только сам участник включает его себе. Ограничиваемся **capacity 1→2**
(булев тоггл); capacity 3 не делаем — добавим позже отдельной задачей, если понадобится.

**Почему не «глобально для всех» (отвергнутая альтернатива):**
- Аффорданс подтверждения «можно выбрать несколько кругов» стал бы дефолтом для 90%,
  кто хочет одну книгу.
- Доска сценариев замусорилась бы дублированием людей по кругам даже для моно-читателей.
- Ранжирование книг («вот мой порядок из 5 книг») означает «готов на любую одну из них»,
  а не «готов читать все» — глобальный capacity исказил бы смысл ранжирования.

Opt-in сохраняет сегодняшний UX бит-в-бит для моно-читателей.

## Как это выглядит для пользователя

1. Участник с включённым тогглом видит кнопку «Хочу в этот круг» у **нескольких** кругов
   (по разным книгам), а не только у одного.
2. Он может подтвердить до **2** кругов — по одному на книгу (два круга одной книги нельзя).
3. Он попадает в 2 читательских круга и читает 2 книги.
4. Моно-читатели (тоггл выключен) видят и делают ровно то же, что сейчас.

## Ключевое наблюдение: настоящая сложность — в подтверждениях, не в движке

Старый план в комментарии issue покрывал только генерацию сценариев (~1 из 7 слоёв работы)
и пропустил, что модель подтверждений/замыкания кругов жёстко зашита на «один круг = юзер»:
- БД: PK таблицы подтверждений на `(session, user)` — физически один выбор на юзера.
- API `set_confirmation` — семантика «заменить единственный выбор».
- Каскад замыкания (`runConfirmationCascade`): при локе круга **все** его участники
  полностью выбывают из подбора.

Всё это должно стать «до N подтверждений на юзера, по одному на книгу».

Старый план также предлагал вернуть coverage-first сортировку сценариев — это **отвергнуто**:
движок недавно осознанно упростили до satisfaction-ранжирования с Парето-отсечением
неполных сценариев (PR #437). Меняем **только** ограничение «один круг на юзера»,
ранжирование не трогаем.

## Архитектура (7 слоёв)

### Слой 1 — БД (миграции)
- `matching_session_participants`: добавить `reading_capacity integer not null default 1`
  + CHECK `reading_capacity IN (1, 2)`. Таблица аудируемая; колонка не чувствительная —
  маскирование в `audit_capture()` не нужно, но новую таблицу/колонку покрывает существующий
  триггер (проверить, что триггер захватывает новую колонку).
- `matching_circle_confirmations`: сменить PK `(session_id, user_id)` →
  `(session_id, user_id, book_id)`. Добавить явную колонку `book_id` (сейчас в таблице есть
  `circle_key`, но нет `book_id`; парсинг книги из ключа — хрупко). Обновить/добавить триггер
  аудита на изменённую таблицу (`matching_circle_confirmations` уже в `AUDITED_TABLES`).
- Шаблон триггера — `drizzle/0040_audit_triggers.sql`; синхронность реестра и триггеров
  проверяет `drizzle/0040_audit_triggers.test.ts`.

### Слой 2 — capacity API
- `PATCH /api/matching/sessions/:id/capacity` с телом `{ capacity: 1 | 2 }`.
- Валидация: авторизован; является активным участником сессии; сессия **не** frozen.
- **Развилка А (зафиксировано):** нельзя понизить capacity 2→1, пока у участника **2**
  активных подтверждения. API возвращает ошибку с понятным сообщением; участник должен
  сперва сам отменить один круг. Никакой тихой инвалидации.
- **Развилка Б (зафиксировано):** админ **не** может менять чужой capacity. Только сам
  участник. (Пункт старого плана про admin impersonation вырезан из скоупа.)
- Изменение capacity делает broadcast `state_changed` → сценарии пересчитываются live.
- Мутации — через `withAuditContext` (`source: 'matching'`, actor = сам участник).

### Слой 3 — движок сценариев (`lib/matching/scenarios.ts`)
- `CircleState.usedUserIds: Set<string>` → `assignmentsByUser: Map<string, number>`.
- `canAddCircle`: круг добавим, если книга ещё не использована в сценарии **и** для каждого
  участника круга `assignmentsByUser.get(user) < capacity[user]`. (Книга по-прежнему —
  максимум один круг на сценарий.)
- `addCircle`: инкремент счётчика по каждому участнику.
- Один и тот же участник не может дважды попасть в один круг/книгу (гарантируется тем, что
  участник в `signupsByBook` для книги фигурирует один раз).
- `leftOut` уже считается по уникальным участникам (`toScenario`, Set) — не трогаем.
- Ранжирование `compareScenarioSatisfaction` + `filterDominatedScenarios` — **не трогаем**.
- Вход движка получает per-user capacity (проброс из scenario-input-db).
- **Перформанс:** opt-in означает cap-2 у единиц участников, ветвление растёт ограниченно.
  Оставляем текущие `BEAM_WIDTH=50` / `MAX_TOTAL_CIRCLES=900`, но добавляем нагрузочный
  unit-тест (worst case: все участники cap-2, N ≈ реальный максимум сессии) как страховку от
  комбинаторного взрыва. Если тест покажет деградацию — вводим отдельный лимит на число
  cap-2-участников или снижаем beam для таких состояний (решаем по факту теста).

### Слой 4 — каскад подтверждений (`lib/matching/confirmation-reconciliation.ts`)
Ядро переписывается на счётчик-модель. **Инвариант: при всех capacity = 1 поведение
схлопывается бит-в-бит в текущее** (обратная совместимость by construction).
- `runConfirmationCascade`: состояние `activeUserIds: Set` →
  `remainingCapacity: Map<userId, number>` + `lockedBooksByUser: Map<userId, Set<bookId>>`.
- Лок круга: для каждого участника декремент `remainingCapacity` и добавление `bookId` в его
  locked-set. Участник **не** выбывает глобально, пока остаётся ёмкость.
- `recompute(...)`: получает `remainingCapacity` и `lockedBooksByUser` вместо плоского
  active-сета (движок исключает круги по книгам, которые участник уже замкнул, и участников
  с нулевым остатком ёмкости).
- Гарантия прогресса: суммарная остаточная ёмкость строго убывает на каждый лок; верхняя
  граница итераций = сумма capacity всех участников (а не число участников).
- `reconcileConfirmations`:
  - `confirmationsByUser` → ключ `userId:bookId`; исключение о дубле только для одной книги.
  - `circlesToLock`: условие «у участника есть подтверждение **на эту книгу**, указывающее
    на этот круг».
  - Исключение кругов (`rankedCurrentCircles`): круг недоступен, если участник уже замкнул
    эту книгу или исчерпал ёмкость (а не «участник вообще locked»).
- Edge cases под тест: (1) участник подтвердил 2 круга, книга A лочится первой — подтверждение
  на B переживает лок; (2) greedy-порядок локов не рушит сходимость (доказывается убыванием
  суммарной ёмкости).

### Слой 5 — UI (`components/nd/MatchingScenarios.tsx`, рабочая область matching)
- **Тоггл «Готов читать 2 книги за раз»** — рядом с личным списком в рабочей области matching
  (точное место — при вёрстке). Дефолт выключен. Скрыт/задизейблен на frozen-сессии и для
  observer. Стиль — по `/styleguide`, токены, без литералов цвета.
- **Confirm-аффорданс:** проп `viewerConfirmedCircleKey: string | null` → множество ключей
  (`viewerConfirmedCircleKeys: string[]`). Кнопка «Хочу в этот круг» видна, пока
  `подтверждено < capacity` **и** на книгу этого круга ещё нет подтверждения.
- **Участник в двух кругах:** его псевдоним честно рендерится в обоих кругах. Когда `ref`
  встречается в сценарии более одного раза — метка у чипа (напр. «читает 2»), чтобы не
  выглядело багом.
- **Развилка А в UI:** тоггл off заблокирован при 2 активных подтверждениях с подсказкой
  «сначала отмени один круг».

### Слой 6 — тесты
- **Unit движок:** cap1 = текущее поведение; cap2 позволяет одному участнику замкнуть 2 круга;
  сценарий с 2 кругами ранжируется корректно; `leftOut` по уникальным; нагрузочный тест
  (все cap-2).
- **Unit каскад:** cap1 = весь текущий набор тестов без изменений; cap2 — оба круга лочатся;
  лок книги A не рушит подтверждение на B; сходимость каскада.
- **API:** capacity PATCH (auth, validation, frozen, broadcast); понижение 2→1 при 2
  подтверждениях отклоняется; multi-confirm не превышает capacity; два круга одной книги
  запрещены.
- **E2E:** участник включает тоггл → подтверждает 2 круга → **reload** → оба сохранились
  (персистентность после перезагрузки). Файл — расширить `e2e/matching-satisfaction.spec.ts`
  или новый; следовать гочам из `docs/features/testing.md`.
- **UI Layout:** если тоггл/метка «читает 2» имеют CSS-поведение (скрытие/позиционирование) —
  тест boundingBox в `e2e/ui-states.spec.ts`.

### Слой 7 — документация
- `docs/wiki/`: обновить модель матчинга, БД-схему (PK confirmations + `reading_capacity`),
  API endpoints (`public/openapi.json` при необходимости), пользовательский workflow.
- `docs/features/`: обновить code-level описание matching (генерация сценариев, каскад,
  подтверждения).

## Зафиксированные решения

- **А.** Понижение capacity при двух подтверждениях — **блокируется** (участник сам отменяет
  круг). Без тихой инвалидации.
- **Б.** Админ-установка capacity — **вне скоупа**. Только сам участник.
- **В.** В `matching_circle_confirmations` добавляется явная колонка `book_id` (PK на
  `(session, user, book)`), а не парсинг из `circle_key`.
- **Ранжирование** сценариев — satisfaction + Парето, **без изменений** (не возвращаем
  coverage-first сортировку из старого плана).
- **Границы capacity** — только 1→2 (булев тоггл); 3 отложено.

## Что вне скоупа

- capacity 3.
- Админ-установка чужого capacity.
- Возврат coverage-first ранжирования сценариев.
- Любые изменения ранжирования кругов/сценариев помимо снятия ограничения «один круг/юзер».
