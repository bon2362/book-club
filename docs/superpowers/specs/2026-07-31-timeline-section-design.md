# Раздел Timeline: перенос локального приложения в book-club

**Дата:** 2026-07-31
**Статус:** дизайн согласован, план реализации не написан

## Задача

Перенести локальное приложение `~/documents/timeline` (личные исторические
таймлайны) в сайт книжного клуба так, чтобы владелец проекта создавал таймлайны
в админке, а поделиться каждым можно было публичной ссылкой.

## Что представляет собой исходное приложение

Локальное десктопное приложение: React 19 + Fastify + SQLite + Vite.
19 983 строки кода, 29 009 строк тестов (1059 тестов в 107 файлах).

Доменная модель:

- **Общие справочники** — события, эпохи, типы событий (задают цвет и иконку),
  изображения.
- **Таймлайн — это подборка**, а не собственный набор событий. Событие заводится
  один раз и включается в несколько таймлайнов; на каждом у него могут быть своя
  заметка, цвет, видимость.
- **Даты исторические**: год + эра (BCE/CE), месяц и день опциональны,
  поддерживаются периоды и признак «продолжается по сей день».
- Описания — форматированный текст (Tiptap, хранится как HTML) с изображениями.
- Рендер — горизонтальная лента с масштабированием, слоем эпох, фильтрами,
  панелью деталей.
- Дополнительно: локальные бэкапы, разовый импорт из TimelineJS CSV.

Накопленные данные: 2 таймлайна («Всеобщая история», «Заря всего»), 28 событий,
14 эпох, 2 типа событий, 2 изображения.

## Принятые решения

| Решение | Выбор |
|---|---|
| Смысл «ссылок» | Публичный адрес самого таймлайна для шаринга |
| Права | Создаёт только владелец (админ), смотрят все без входа |
| Модель данных | Сохраняем общую базу событий и подборки, как в исходнике |
| Существующие данные | Переносим одноразовым скриптом |
| Внешний вид | Переверстать под дизайн-систему сайта |
| Мобильные | Десктоп-онли на старте, полноценные мобильные — позже |
| Объём | Реализация этапами, план покрывает все этапы |

## Границы переносимости

Разделение по критерию «пересекает ли код границу стека».

**Переносится практически копипастом (~1500 строк):**

- `src/shared/historical-date/` — арифметика исторических дат (152 строки).
- `src/client/features/timeline/geometry/` — расчёт раскладки ленты: координаты
  по времени, распределение по дорожкам, плотность, засечки линейки,
  соединители (~730 строк). Не знает ни про базу, ни про сервер.
- `src/shared/contracts/` — схемы данных на zod (у нас zod той же версии).
- Компоненты рендера — JSX и логика взаимодействия.

**Переписывается под наш стек:**

- Слой данных: 5 репозиториев + 6 наборов маршрутов (~2800 строк), написаны под
  SQLite и Fastify.
- Роутинг: `react-router` в 24 файлах → App Router.
- Загрузка данных: `@tanstack/react-query` в 37 файлах. На публичных страницах
  библиотека не нужна — данные читаются на сервере средствами App Router.
  Потребность в ней возникает только на админских экранах (этапы 4–5); решение,
  добавлять ли зависимость, принимается там.
- Стили: 2703 строки собственного CSS → токены `app/globals.css`.
- React 19 → React 18.

**Не переносится:** бэкапы (Neon бэкапит сам), импорт TimelineJS (был разовый),
загрузка файлов изображений, разделитель панелей с перетаскиванием.

## Архитектура

### Схема данных

Шесть новых таблиц в Neon Postgres через Drizzle. Префикс `historical_` у
справочников выбран, чтобы не конфликтовать с существующими `matching_events` и
`user_activity_events`.

| Таблица | Содержимое |
|---|---|
| `historical_event_types` | Тип события: название, цвет, иконка |
| `historical_events` | Событие: название, тип, даты (год/эра/месяц/день, начало и конец, признак ongoing), описание в markdown, адрес картинки, подпись |
| `historical_epochs` | Эпоха: название, период, описание, картинка |
| `timelines` | Подборка: название, описание, `slug`, `published`, сохранённые настройки вида |
| `timeline_events` | Связь таймлайн↔событие + локальная заметка |
| `timeline_epochs` | Связь таймлайн↔эпоха + цвет, видимость, закреплённая дорожка |

Все шесть таблиц добавляются в `AUDITED_TABLES` (`lib/audit/audited-tables.ts`) и
получают аудит-триггеры отдельной миграцией по шаблону
`drizzle/0040_audit_triggers.sql`.

### Отличия от исходной схемы

1. **Таблица `images` не переносится.** Вместо неё поле с внешним адресом
   картинки прямо в событии и эпохе — как `cover_url` у книг. Снимает слой
   хранилища файлов, хеширования и уборки осиротевших файлов (~600 строк кода и
   тестов). На Vercel файловая система эфемерна, локальное хранилище там
   невозможно без Vercel Blob.
2. **Описания хранятся в markdown, а не в HTML.** В проекте markdown повсюду
   (`react-markdown`, `MarkdownToolbar`). Конвертация выполняется один раз при
   переносе 42 записей и проверяется глазами. Убирает зависимости Tiptap
   (4 пакета) и `sanitize-html`.
3. **Добавлены `slug` и `published`** — нужны для публичных ссылок, в локальном
   приложении их не было. Slug задаётся вручную латиницей; для двух
   существующих таймлайнов проставляется при переносе.

### Размещение кода

```
lib/timeline/
  historical-date.ts      — арифметика дат (порт)
  geometry/               — расчёт раскладки (порт)
  queries.ts              — чтение из Postgres
  mutations.ts            — запись через withAuditContext
app/timeline/
  page.tsx                — список опубликованных
  [slug]/page.tsx         — сам таймлайн
app/api/admin/timeline/   — CRUD справочников и подборок
components/nd/timeline/   — компоненты ленты на токенах проекта
scripts/import-timeline-sqlite.ts — одноразовый перенос данных
```

### Доступ

Чтение `/timeline` и `/timeline/[slug]` — без авторизации, только записи с
`published = true`. Все мутации — через админские маршруты с проверкой роли,
обёрнутые в `withAuditContext`.

## Этапы

### Этап 0 — аудит тестов

Выполняется до переноса, на исходном репозитории. Резать предстоит только те
тесты, что реально переезжают: geometry и historical-date, 9 файлов, ~800 строк.
Остальные 1000+ тестов отпадают вместе с кодом, который они проверяют
(бэкапы, импорт TimelineJS, Fastify-маршруты, SQLite-репозитории,
покомпонентные тесты форм под старую вёрстку).

Критерии, по которым тест удаляется:

- проверяет то же, что уже проверено другим тестом на соседней ветке условия;
- проверяет реализацию, а не поведение (внутренние вызовы, порядок операций);
- тавтологичен — упадёт только если сломать сам тест;
- проверяет тривиальную обёртку без логики;
- перебирает значения там, где достаточно границ диапазона.

Критерии, по которым тест остаётся:

- граничный случай, невидимый глазами (переход «до н.э. → н.э.», событие без
  даты окончания, пересечение периодов, нулевой диапазон);
- расчёт, ошибка в котором даёт правдоподобный, но неверный результат.

Результат этапа — отчёт с фактическими цифрами «было / стало» по каждому файлу.
Целевой ориентир: оставить только тесты, попадающие под критерии сохранения, —
ожидаемый порядок величины после реза измеряется единицами файлов, а не девятью.
Итоговая цифра фиксируется по факту и не подгоняется под цель: тест, покрывающий
перечисленный граничный случай, не удаляется ради красивой статистики.

### Этап 1 — чистые расчёты

Перенос `historical-date` и `geometry` в `lib/timeline/` вместе с прошедшими
аудит тестами. Пользовательских изменений нет. Отдельный PR: проверяется
однозначно — тесты зелёные или нет.

### Этап 2 — схема и перенос данных

Миграция Drizzle с шестью таблицами, регистрация в `AUDITED_TABLES`, миграция с
аудит-триггерами. Скрипт `scripts/import-timeline-sqlite.ts` читает
`data/timeline.sqlite`, конвертирует даты и описания (HTML → markdown),
переносит адреса картинок, печатает отчёт о количестве перенесённых записей.
Интерфейса ещё нет.

### Этап 3 — публичный просмотр

Страницы `/timeline` (список) и `/timeline/[slug]` (лента). Порт
`TimelineRenderer`, `EventLayer`, `EpochLayer` на токены проекта. На узком
экране — простой вертикальный список событий без ленты. Ссылка для шаринга
начинает работать.

Тесты: E2E на открытие таймлайна по ссылке неавторизованным пользователем;
layout-тест с `boundingBox()` на геометрию ленты в `e2e/timeline-layout.spec.ts`.

### Этап 4 — справочники в админке

Вкладка «Таймлайны» в `AdminPanel` рядом с «Каталогом». Формы создания и правки
событий, эпох, типов: поля исторических дат с эрами, выбор цвета,
markdown-редактор на существующем `MarkdownToolbar`. Маршруты
`app/api/admin/timeline/*`, мутации через `withAuditContext`.

После этого этапа локальное приложение больше не нужно.

### Этап 5 — сборка таймлайна

Экран подборки: добавление и удаление событий и эпох, локальная заметка, цвет
эпохи, видимость. Создание таймлайна с указанием slug и публикацией. Порт самого
крупного файла исходника (`TimelineContentsPage`, 1009 строк) — вынесен в
отдельный этап по объёму.

Тесты: E2E на полный цикл «создать событие → добавить в таймлайн → увидеть на
публичной странице», с перезагрузкой страницы для проверки персистентности.

### Этап 6 — тонкие настройки (опционально)

Сохранённый масштаб и положение ленты, фильтры по типам событий, боковая панель
деталей, отмена действия. Раздел полностью работоспособен и без них.

### Этап 7 — мобильная версия (отложено)

Полноценная вертикальная лента вместо простого списка.
