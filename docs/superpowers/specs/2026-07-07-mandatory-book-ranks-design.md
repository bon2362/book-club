# Обязательный ранг у каждой записи на книгу

**Дата:** 2026-07-07
**Статус:** дизайн утверждён, ожидает плана реализации

## Проблема

На сайте два раздельных понятия:

- `signup_books` — «мне интересна книга» (запись);
- `book_priorities` — «место книги в моём приоритете» (ранг).

Флаг `users.priorities_set` кодирует двухфазную модель: сначала отметить книги, потом отдельно перетащить их по приоритету. Матчинг (`generateSatisfactionScenarioSets` → `filterRankedSignups`, `lib/matching/scenarios.ts`) учитывает **только** записи с рангом. Записи без ранга («без ранга») молча выпадают из всех сценариев.

Продуктовый gap: пользователь вступает в сессию, добавляет книги с каталога, ожидает, что они участвуют в матчинге — а они не участвуют, потому что ранг не проставлен. Реальный случай: книга «Краткая история неолиберализма» с 3 записавшимися активными участниками не попала ни в один сценарий (2 из 3 без ранга при `minGroupSize = 3`).

Дополнительный источник записей без ранга: возврат книги из статуса «Читаю/Прочитал» в `null` не восстанавливает ранг (`changeStatus`, `lib/matching/session-transition-db.ts:513`).

## Цель

Исключить состояние «записан, но без ранга» на всём сайте. Любая добавленная книга сразу получает ранг = её позиция в списке приоритетов.

## Утверждённые продуктовые решения

1. **Авто-ранг = полноценный ранг.** Позиция при добавлении сразу считается силой интереса: `rank ≤ 3` → «очень хочу», `> 3` → «хочу» (`interest()` в `lib/matching/scenarios.ts` не меняется).
2. **Новая книга добавляется в конец списка** (`rank = max+1`). Существующие приоритеты не сдвигаются.
3. **Бэкфилл — глобальный** (все сессии, не только активная): существующие ранги сохраняются; записи без ранга дописываются в конец по `signed_at`.
4. **Различаем «авто» и «вручную» на уровне каждой книги** — новая колонка `book_priorities.rank_source` со значениями `'auto' | 'manual'`.

## Инвариант

> Каждая запись `signup_books` с `personal_status = null` имеет ровно одну строку `book_priorities`.
> Книги со статусом `reading` / `read` строки `book_priorities` не имеют (исключены из матчинга — поведение сохраняется).

## Архитектура (Вариант C — хаб-хелпер на существующих choke-points)

Вся логика ранжирования централизуется в одном переиспользуемом хелпере, вызываемом из двух точек, через которые и так проходят все мутации `signup_books` / `book_priorities`:

- `lib/signup-books.ts` (`upsertSignupByBookIds`) — путь каталог-формы, в том числе когда активной сессии нет;
- `MatchingTransitionExecutor` в `lib/matching/session-transition-db.ts` — путь доски матчинга и профиля при активной сессии.

Отвергнутые варианты: A («инструкция на каждый путь мутации») — риск, что будущий путь снова создаст запись без ранга; B (триггер в БД) — конфликтует с audit-триггерами, засоряет журнал `source='trigger'`, усложняет проставление `rank_source` и тесты.

### Хелпер

```
ensureRankForSignup(tx, userId, bookId, source: 'auto' | 'manual'): appends rank = (max existing rank)+1
                                                                    если строки ещё нет; иначе no-op
compactRanks(tx, userId): переиндексация rank = 1..N по возрастанию после удаления
```

Оба вызываются только внутри уже открытых транзакций/`withAuditContext`, чтобы аудит фиксировал actor.

## Матрица мутаций

| Событие | Сейчас | Станет |
|---|---|---|
| Добавить книгу (каталог/доска, `status=null`) | insert signup, ранга нет | insert signup + `ensureRankForSignup(..., 'auto')` |
| Явный reorder (drag / `PUT /api/priorities` / `reorder_priorities`) | set ranks, `priorities_set=true` | set ranks + `rank_source='manual'` для затронутых книг |
| `status: null → reading/read` | delete rank + компактизация | без изменений |
| `status: reading/read → null` | ранг не возвращается (баг) | `ensureRankForSignup(..., 'auto')` |
| Убрать книгу (`change_book remove`) | delete rank + компактизация | без изменений |
| `replaceSignup` (каталог-форма) | новым книгам ранг не ставит | новым — `ensureRankForSignup(..., 'auto')`; сохранённым книгам ранг и `rank_source` не трогаем |

**Правило `rank_source`:** `'manual'` проставляется **только** при явном reorder/drag. Авто-append и бэкфилл всегда `'auto'`. Книга, единожды тронутая руками, остаётся `'manual'`, пока следующий reorder не перезапишет её.

Затрагиваемые пути записи (все должны соблюдать инвариант; проверить каждый):
`app/api/signup/route.ts`, `app/api/priorities/route.ts`, `app/api/matching/priorities/route.ts`, `app/api/matching/books/route.ts`, `app/api/signup-books/[bookId]/status/route.ts`, admin-пути (`app/api/admin/*`), `lib/admin/user-merge.ts`, тест-эндпоинты `app/api/test/*`.

## Схема БД и бэкфилл

- Новая колонка `book_priorities.rank_source text not null default 'auto'` (миграция Drizzle + добавить в схему `lib/db/schema.ts`).
- `book_priorities` — уже аудируемая таблица; `rank_source` не чувствительная колонка, маскирование в `audit_capture()` не требуется. Проверить, что реестр `AUDITED_TABLES` и триггеры остаются согласованными (тест `drizzle/0040_audit_triggers.test.ts`).
- **Бэкфилл-миграция:**
  - существующим строкам `book_priorities` проставить `rank_source = 'manual'` (они могли появиться только через явный reorder, который выставлял `priorities_set=true`);
  - для каждого пользователя: записи `signup_books` с `personal_status = null` и без строки `book_priorities` — дописать в конец (после максимального существующего ранга), упорядочив по `signed_at`, с `rank_source = 'auto'`;
  - выполняется глобально по всем пользователям и сессиям.
- Бэкфилл идёт отдельной миграцией и в журнале аудита помечается как системная операция (`source: 'system'`, `actorUserId: null`), а не через молчаливый триггер (`source='trigger'`).

## Судьба `priorities_set`

Флаг становится производным от наличия хотя бы одной `manual`-книги. Не удаляем колонку в этой итерации (широкий радиус изменений: админ-сортировка `app/api/admin/priorities/route.ts`, merge `lib/admin/user-merge.ts`, UI, тесты). Вместо этого:

- при явном reorder продолжаем ставить `priorities_set = true` (как сейчас);
- гранулярный сигнал «авто/вручную» даёт `rank_source` — именно он показывается админу.

Удаление колонки `priorities_set` — возможный последующий рефактор, вне scope этой спеки.

## Аудит / логирование

- Все авто-проставления ранга идут через `withAuditContext` на существующих choke-points → в журнале виден actor, `action='insert'`, `entity_type='book_priorities'`, корректный `source` (`catalog` / `matching` / `profile`).
- Бэкфилл-миграция — системная операция (`source='system'`, `actorUserId=null`).
- Не должно появляться записей `source='trigger'` для `book_priorities` (признак мутации мимо `withAuditContext`).

## Тестирование

Unit:
- добавление книги (каждый путь) → создаётся `book_priorities` с корректным рангом и `rank_source='auto'`;
- возврат из `reading/read` в `null` → ранг восстанавливается (`'auto'`);
- явный reorder → `rank_source='manual'` для затронутых, `priorities_set=true`;
- `replaceSignup` → новым книгам ранг проставлен, сохранённым `rank_source` не сброшен;
- бэкфилл: после миграции нет `signup_books (status=null)` без `book_priorities`; существующие ранги сохранены и помечены `'manual'`; дописанные — `'auto'` в порядке `signed_at`;
- матчинг: книга с ранее «безранговыми», а теперь ранжированными записями попадает в сценарии.

E2E (Playwright, `page.reload()` обязателен):
- профиль: добавить книгу → перезагрузка → книга с рангом на месте;
- (по необходимости) новый текст баннера.

Инвариант-тест: перебор всех путей мутации не оставляет записи `status=null` без ранга.
