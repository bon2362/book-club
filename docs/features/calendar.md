# Circle Calendar

Календарь круга помогает участникам согласовать время встречи внутри сайта. Свободное время хранится глобально у пользователя, а страница согласования привязана к конкретному кругу книги.

## Адреса

- Страница: `GET /calendar/[slug]`
- Resolver из матчинга: `GET /calendar/circle/[bookId]/[position]`
- Состояние: `GET /api/calendar/[slug]`
- Свободное время: `PUT /api/calendar/availability`
- Встречи: `POST /api/calendar/[slug]/meetings`, `DELETE /api/calendar/[slug]/meetings/[id]`
- Длительность и админский slug: `PATCH /api/calendar/[slug]`
- Часовой пояс: `PATCH /api/profile/timezone`

### Telegram Mini App API

Mini App передаёт подписанный Telegram `initData` в заголовке `Authorization: tma <initData>`. Страница `/tg/calendar/[slug]` первой подключает официальный SDK `https://telegram.org/js/telegram-web-app.js?65`: именно он создаёт `window.Telegram.WebApp` и кладёт в него `initData`. Сервер проверяет подпись и находит уже привязанный Telegram identity; новый аккаунт по этому пути не создаётся. Участие в круге проверяется до каждого чтения и изменения.

- `GET /api/tg/calendar/[slug]` — состояние только для участника круга;
- `PUT /api/tg/calendar/[slug]/availability` — сохраняет интервалы текущего участника;
- `POST /api/tg/calendar/[slug]/meetings` — назначает встречу после повторной серверной проверки кандидата под блокировкой пространства круга.

### Календарь в теме форума Telegram (пилот)

Спека — `docs/superpowers/specs/2026-11-22-telegram-group-calendar-pilot-design.md`. Источник данных тот же: `user_availability`, `circle_schedules`, `circle_meetings`; отдельной таблицы голосов нет.

- **Привязка.** Таблица `telegram_calendar_topics` (миграция `drizzle/0067_telegram_calendar_topics.sql`, аудируется): `schedule_id`, `chat_id`, `message_thread_id`, `announcement_message_id`. Уникальность — `(chat_id, message_thread_id)`: одна тема ведёт к одному календарю. Один `schedule_id` может быть привязан к нескольким темам (тестовая и рабочая группа). `id` строки — непрозрачный id для кнопок и Direct Link.
- **Команда.** В теме группы администратор сайта (`user.is_admin`, Telegram привязан к его аккаунту) пишет `/calendar@<бот> <slug>`; форма `/calendar <slug>` тоже принимается, но при privacy mode Telegram может не доставить её боту. Повторная команда в той же теме обновляет привязку и сообщение, а не создаёт дубль. Обычный участник и непривязанный Telegram получают отказ в теме. Вне темы (личка, «General») команда не работает.
- **Быстрые кнопки** (`lib/calendar/telegram-quick-slots.ts`). Только будущие блоки полной длительности встречи, подписи в `Europe/Belgrade` с CET/CEST. Пока в круге никто не отметил время — шесть ближайших слотов ритма вт/чт 19:00, сб/вс 12:00 в пределах 14 дней. После первой отметки — до шести реальных стартов (шаг 30 минут, весь блок внутри интервала участника), сортировка по числу отметивших, затем по времени; прошедшие и пересекающие встречу круга исключены. Если после первой отметки годных стартов не осталось (всё отмеченное занято встречей), возвращаются базовые слоты, чтобы у сообщения не пропали кнопки.
- **Нажатие** (`callback_data = calendar:<bindingId>:<unixSeconds>`). Webhook сверяет `chat.id` и `message_thread_id` сообщения с сохранённой привязкой, находит уже привязанный Telegram identity (`resolveTelegramBotCalendarActor`, аудит-источник `telegram-bot`), проверяет участие **именно в этом круге** (админство сайта членство не заменяет) и добавляет/снимает ровно один блок длительности: в `saveCalendarAvailability` уходит полный нормализованный список, остальные интервалы человека не трогаются. Клавиатура общая для темы — в кнопках только общие счётчики, личное «Отмечено»/«Снято» приходит toast'ом `answerCallbackQuery`.
- **Сообщение темы** (`publishTelegramTopicAnnouncement`). Читается без зрителя, редактируется по `announcement_message_id`; «message is not modified» — успех; «message to edit not found» — отправляется ровно одна замена в ту же тему и сохраняется новый id. Прочие ошибки Telegram замену не создают.
- **Полная сетка.** URL-кнопка `https://t.me/<бот>?startapp=calendar_<bindingId>` открывает Main Mini App поверх темы (web_app-кнопки в группах Telegram не разрешает). Страница `/tg/topic-calendar` берёт `start_param` из `initDataUnsafe` (запасной путь — `tgWebAppStartParam` в адресе), вызывает `GET /api/tg/calendar/topic/[bindingId]` (подписанный `initData` + участие в круге → только `{ slug }`) и монтирует обычный `TelegramCalendarClient`. После успешного сохранения клиент вызывает `POST /api/tg/calendar/topic/[bindingId]` (debounce 800 мс, при закрытии Mini App — `keepalive`), сервер обновляет сообщение темы.
- **Webhook обязан получать `callback_query`.** Регистрация: `node --env-file=.env.local scripts/telegram-set-webhook.mjs` (выставляет `allowed_updates: ["message", "callback_query"]`). Если webhook зарегистрирован только на `message`, кнопки молча не работают.
- **Миграция `0067`** применяется вручную: `node --env-file=.env.local scripts/apply-migration.mjs drizzle/0067_telegram_calendar_topics.sql`. До неё бот отвечает «нужна миграция базы», topic API — `409 migration_required`.

Resolver нужен, чтобы не создавать `circle_schedules` внутри read-модели matching. Он лениво создаёт пространство календаря и редиректит на канонический slug.

## Данные

Миграция `drizzle/0062_calendar.sql` добавляет:

- `user.timezone`, `user.timezone_confirmed`;
- `user_availability` — интервалы свободного времени пользователя;
- `circle_schedules` — пространство календаря по `session_id + book_id + position`;
- `circle_meetings` — назначенные и отменённые встречи.

Новые мутабельные таблицы внесены в `AUDITED_TABLES` и получают `audit_capture()` triggers. Все writes идут через `withAuditContext`.

## Логика

Чистые модули лежат в `lib/calendar/`:

- `slots.ts` — получасовая арифметика и окно 28 дней;
- `availability-intervals.ts` — normalize/add/remove/clamp интервалов;
- `busy.ts` — вычитание встреч из свободного времени;
- `overlap.ts` — наложение и правило кандидата;
- `slug.ts` — транслитерация адресов;
- `telegram-quick-slots.ts` — быстрые варианты для сообщения темы Telegram;
- `telegram-topic-calendar.ts` — привязка темы, проверка происхождения кнопки и членства, toggle одного блока, публикация сообщения;
- `telegram-topic-webhook.ts` — разбор `/calendar` и `callback_query` для webhook;
- `schedule-db.ts` и `public-state.ts` — DB-сборка состояния.

Кандидат на встречу появляется, когда свободны все отметившиеся участники, отметившихся минимум двое, слот не в прошлом, встреча помещается в окно и не пересекается с уже назначенной встречей.

## Production Rollout

Миграция `0062_calendar.sql` не применяется автоматически в production. До ручного прогона:

- `GET /api/calendar/[slug]` возвращает состояние с `migrationRequired: true`;
- мутирующие календарные API отвечают `409 migration_required`;
- страница `/calendar/[slug]` показывает заглушку вместо 500.

После production-деплоя оператор применяет миграцию:

```bash
node --env-file=.env.local scripts/apply-migration.mjs drizzle/0062_calendar.sql
```

## UI

Компоненты находятся в `components/nd/Calendar*.tsx`. Цвета и геометрия используют токены из `app/globals.css`; прозрачные зелёные ступени задаются через `color-mix(in srgb, var(--success) N%, transparent)`.

Обычный клик по свободной клетке сразу сохраняет интервал длительностью `durationMinutes`; подтверждающий popover не нужен для отметки свободного времени. Клик по любой клетке внутри своего отмеченного блока снимает весь duration-sized блок, а не отдельные 30 минут. В БД при этом остаётся нормализованный список интервалов: атомарность блока — правило UI-операции, а не отдельная таблица слотов. Popover остаётся для просмотра занятости, своей уже отмеченной клетки и назначения встречи. Длительность встречи редактируется select-контролом в шапке и сохраняется через `PATCH /api/calendar/[slug]`.

Список участников на desktop работает в двух режимах: hover временно фильтрует сетку до календаря участника, click для админа открывает `/calendar/[slug]?as=<userId>` и переводит редактирование на выбранного участника. В админском режиме `?as=<userId>` сетка по умолчанию показывает календарь выбранного участника, а не общее наложение круга; общее пересечение всё ещё используется для popover и назначения встречи. На touch-устройствах hover недоступен, поэтому tap остаётся только просмотром участника; админское редактирование с телефона возможно по прямой ссылке `?as=<userId>`. Маркер “отмечено вами” рисуется только для текущего редактируемого участника, чтобы при просмотре чужого пустого календаря не оставался чужой уголок.

Публичные страницы `/calendar/[slug]` не монтируют клиентский `SessionProvider`, чтобы не делать лишний `GET /api/auth/session`. PostHog остаётся подключённым для pageview/events, но remote feature flags отключены через `advanced_disable_flags`, чтобы не было фоновых `/flags`-запросов.

Клавиатурная доступность сетки не входит в первую версию и вынесена в issue #537.

## Часовые пояса

Сетка, границы дней, карточка встречи и попап рисуются в поясе смотрящего. Пояс — **состояние страницы** (`CalendarClient`), а не вычисление во время рендера. Начальное значение детерминированное: сохранённый в профиле пояс, иначе UTC. Браузерный пояс подставляется в `useEffect` после монтирования.

Это не украшение, а обязательное условие. Первый рендер делает сервер, у которого `Intl` вернёт пояс сервера; если подставлять браузерный пояс прямо в рендере, серверная разметка уедет в UTC, а гидратация подписи уже не перепишет — анонимный посетитель навсегда останется с UTC-сеткой. Так и было в первой версии фикса.

Полоса выбора пояса управляемая и показывается **всем, включая анонимных**: у анонимного нет профиля, поэтому выбор действует только в его вкладке и ничего не сохраняет; у участника выбор пишется в профиль. Держать пояс отдельно в полосе и отдельно в сетке нельзя — расхождение между ними уже было багом. Арифметика поясов вынесена в `lib/calendar/timezone.ts`: смещение зоны на конкретный момент, местная полночь, прибавление календарных дней с якорем в полдень (защита от суток длиной 23 и 25 часов), ключ местной даты.

Колонки — местные календарные дни, а не сутки UTC. Строки внутри колонки — 48 получасовок от местной полуночи. В сутки перехода на летнее и зимнее время подписи показывают настоящее местное время, а два слота в году оказываются за пределами колонки; осознанный размен на простоту сетки фиксированной высоты.

В базе по-прежнему абсолютные `timestamptz` — пояс существует только на отображении.

## Тон клетки

Тёмный тон «свободны все» ставится по `candidateCovered`, то есть покрывает всю длительность встречи, а не только её первую клетку. Знаменатель шкалы — число отметившихся (`markedRefs.length`), тот же, что у правила кандидата: иначе при двух отметившихся из четырёх шкала физически не достигала бы максимума.

Тон дублируется в атрибутах `data-tone` (`none | partial | full | focus`), `data-free` и `data-marked`. Это не отладочный мусор, а единственный способ его проверить: jsdom не разбирает `color-mix()` и выбрасывает значение, поэтому `toHaveStyle` на таких стилях проходит при любом проценте.

Фокус на участнике — только явное наведение или тап по имени. Автоматического фокуса в админском режиме нет: он прятал тепловую карту остальных.

## Автосохранение

Правки нумеруются счётчиком `editSeq`, подтверждённый сервером номер хранится в `savedSeq`. Ответ сервера отражает состояние на момент отправки запроса, поэтому пока номера расходятся, серверные интервалы не затирают локальные, а перечитывание состояния после сохранения пропускается. Без этого клики, сделанные за время полёта запроса, откатывались назад и терялись.

## Конкурентность при назначении встречи

Проверка правила кандидата и вставка строки идут в одной транзакции, которая начинается с `select … for update` по строке `circle_schedules`. Без блокировки двое участников одного круга, нажавших «Назначить» одновременно, оба проходили проверку и создавали пересекающиеся встречи: чтение состояния и запись выполнялись разными соединениями.

`fetchCalendarPublicState` принимает соединение и флаг `skipCleanup` — внутри уже открытой транзакции уборка прошлых отметок не запускается, иначе открылась бы вложенная транзакция.

Остаточный случай: два участника **разных** кругов, назначающие пересекающиеся встречи в одну и ту же миллисекунду, блокировкой не покрыты — блокируется пространство, а не человек. Для клуба такого размера это принято сознательно.

## Мобильная раскладка

Порог — 540 px, тот же, что на доске матчинга. Ниже порога: клетка 26 px вместо 22 (в 22 пальцем не попасть) и **одна колонка** вместо `minmax(0, 1fr) 216px` — состав круга уезжает под сетку. Пока раскладка была жёстко двухколоночной, на экране 393 px сайдбар забирал 216 px и колонка дня сжималась примерно до 13 px: сетка формально помещалась в экран, но пользоваться ей было нельзя.

`e2e/calendar-layout.spec.ts` проверяет через `boundingBox()` высоту клетки, отсутствие горизонтальной прокрутки, ширину колонки дня (больше 30 px) и то, что состав круга на узком экране ниже сетки. Ни один из этих дефектов не виден ни в unit-тестах, ни на десктопе.

## Уборка в E2E

`telegram_calendar_topics` каскадится от `circle_schedules`, поэтому удаление пространства в `app/api/test/books` убирает и привязки тем.

Mini App-спеки (`e2e/telegram-calendar-miniapp.spec.ts`, `e2e/telegram-calendar-topic-miniapp.spec.ts`) подменяют `window.Telegram` и **обязаны** отдавать пустой ответ на `https://telegram.org/js/**`: страница грузит настоящий SDK `beforeInteractive`, и он перезаписывает подменённый `WebApp` пустым `initData` — тест видит «Откройте календарь из Telegram».

`circle_schedules.book_id` ссылается на книгу через `restrict`, а `circle_meetings` каскадится от пространства. Поэтому `app/api/test/books` обязан удалять пространства перед книгой: иначе тестовую книгу, для которой открывали календарь, удалить нельзя, teardown падает на внешнем ключе и оставляет мусор в общей e2e-ветке.

Проверки тона в E2E делаются по `data-tone`, а не по `background-color`: фон задан через `color-mix`, браузер возвращает его как `color(srgb …)`, и сравнение вычисленного значения ломается от смены записи цвета, ничего не проверяя по существу.

## Листание дней

Страница показывает семь дней за раз. Набор дней зависит от режима обрезки: в «днях с отметками» это только дни, где кто-то отметился, поэтому страница часто оказывается единственной и обе стрелки штатно отключаются.

Именно поэтому отключённое состояние обязано быть видимым (`opacity: 0.3`, `cursor: not-allowed`), а под диапазоном дат стоит подпись «дни без отметок скрыты». Без них пользователь видит живую на вид стрелку, тап по которой ничего не делает, и считает это поломкой — так и произошло при первой проверке на телефоне. Выход из режима — переключатель «Все дни подряд» под сеткой, там становятся доступны все четыре недели.

На узком экране стрелки — 44×44 px вместо 30×30: прежний размер не годится под палец. Геометрия проверяется в `e2e/calendar-layout.spec.ts`, состояния — в `components/nd/CalendarClient.test.tsx`.

У стрелок есть `aria-label` («Предыдущие дни», «Следующие дни»): сами по себе `‹` и `›` не дают доступного имени. Это не отменяет [#537](https://github.com/bon2362/book-club/issues/537) — сетка по-прежнему недоступна с клавиатуры.
