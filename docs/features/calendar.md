# Circle Calendar

Календарь круга помогает участникам согласовать время встречи внутри сайта. Свободное время хранится глобально у пользователя, а страница согласования привязана к конкретному кругу книги.

## Адреса

- Страница: `GET /calendar/[slug]`
- Resolver из матчинга: `GET /calendar/circle/[bookId]/[position]`
- Состояние: `GET /api/calendar/[slug]`
- Свободное время: `PUT /api/calendar/availability`
- Встречи: `POST /api/calendar/[slug]/meetings`, `DELETE /api/calendar/[slug]/meetings/[id]`
- Длительность и админский slug: `PATCH /api/calendar/[slug]`
- Часовой пояс: `PATCH /api/profile/timezone`

Resolver нужен, чтобы не создавать `circle_schedules` внутри read-модели matching. Он лениво создаёт пространство календаря и редиректит на канонический slug.

## Данные

Миграция `drizzle/0062_calendar.sql` добавляет:

- `user.timezone`, `user.timezone_confirmed`;
- `user_availability` — интервалы свободного времени пользователя;
- `circle_schedules` — пространство календаря по `session_id + book_id + position`;
- `circle_meetings` — назначенные и отменённые встречи.

Новые мутабельные таблицы внесены в `AUDITED_TABLES` и получают `audit_capture()` triggers. Все writes идут через `withAuditContext`.

## Логика

Чистые модули лежат в `lib/calendar/`:

- `slots.ts` — получасовая арифметика и окно 28 дней;
- `availability-intervals.ts` — normalize/add/remove/clamp интервалов;
- `busy.ts` — вычитание встреч из свободного времени;
- `overlap.ts` — наложение и правило кандидата;
- `slug.ts` — транслитерация адресов;
- `schedule-db.ts` и `public-state.ts` — DB-сборка состояния.

Кандидат на встречу появляется, когда свободны все отметившиеся участники, отметившихся минимум двое, слот не в прошлом, встреча помещается в окно и не пересекается с уже назначенной встречей.

## Production Rollout

Миграция `0062` не применяется автоматически в production. До ручного прогона:

- `GET /api/calendar/[slug]` возвращает состояние с `migrationRequired: true`;
- мутирующие календарные API отвечают `409 migration_required`;
- страница `/calendar/[slug]` показывает заглушку вместо 500.

После production-деплоя оператор применяет миграцию:

```bash
node --env-file=.env.local scripts/apply-migration.mjs drizzle/0062_calendar.sql
```

## UI

Компоненты находятся в `components/nd/Calendar*.tsx`. Цвета и геометрия используют токены из `app/globals.css`; прозрачные зелёные ступени задаются через `color-mix(in srgb, var(--success) N%, transparent)`.

Обычный клик по свободной клетке сразу сохраняет интервал длительностью `durationMinutes`; подтверждающий popover не нужен для отметки свободного времени. Клик по любой клетке внутри своего отмеченного блока снимает весь duration-sized блок, а не отдельные 30 минут. В БД при этом остаётся нормализованный список интервалов: атомарность блока — правило UI-операции, а не отдельная таблица слотов. Popover остаётся для просмотра занятости, своей уже отмеченной клетки и назначения встречи. Длительность встречи редактируется select-контролом в шапке и сохраняется через `PATCH /api/calendar/[slug]`.

Список участников на desktop работает в двух режимах: hover временно фильтрует сетку до календаря участника, click для админа открывает `/calendar/[slug]?as=<userId>` и переводит редактирование на выбранного участника. В админском режиме `?as=<userId>` сетка по умолчанию показывает календарь выбранного участника, а не общее наложение круга; общее пересечение всё ещё используется для popover и назначения встречи. На touch-устройствах hover недоступен, поэтому tap остаётся только просмотром участника; админское редактирование с телефона возможно по прямой ссылке `?as=<userId>`. Маркер “отмечено вами” рисуется только для текущего редактируемого участника, чтобы при просмотре чужого пустого календаря не оставался чужой уголок.

Публичные страницы `/calendar/[slug]` не монтируют клиентский `SessionProvider`, чтобы не делать лишний `GET /api/auth/session`. PostHog остаётся подключённым для pageview/events, но remote feature flags отключены через `advanced_disable_flags`, чтобы не было фоновых `/flags`-запросов.

Клавиатурная доступность сетки не входит в первую версию и вынесена в issue #537.

## Часовые пояса

Сетка, границы дней, карточка встречи и попап рисуются в поясе смотрящего. Пояс — **состояние страницы** (`CalendarClient`), а не вычисление во время рендера. Начальное значение детерминированное: сохранённый в профиле пояс, иначе UTC. Браузерный пояс подставляется в `useEffect` после монтирования.

Это не украшение, а обязательное условие. Первый рендер делает сервер, у которого `Intl` вернёт пояс сервера; если подставлять браузерный пояс прямо в рендере, серверная разметка уедет в UTC, а гидратация подписи уже не перепишет — анонимный посетитель навсегда останется с UTC-сеткой. Так и было в первой версии фикса.

Полоса выбора пояса управляемая и показывается **всем, включая анонимных**: у анонимного нет профиля, поэтому выбор действует только в его вкладке и ничего не сохраняет; у участника выбор пишется в профиль. Держать пояс отдельно в полосе и отдельно в сетке нельзя — расхождение между ними уже было багом. Арифметика поясов вынесена в `lib/calendar/timezone.ts`: смещение зоны на конкретный момент, местная полночь, прибавление календарных дней с якорем в полдень (защита от суток длиной 23 и 25 часов), ключ местной даты.

Колонки — местные календарные дни, а не сутки UTC. Строки внутри колонки — 48 получасовок от местной полуночи. В сутки перехода на летнее и зимнее время подписи показывают настоящее местное время, а два слота в году оказываются за пределами колонки; осознанный размен на простоту сетки фиксированной высоты.

В базе по-прежнему абсолютные `timestamptz` — пояс существует только на отображении.

## Тон клетки

Тёмный тон «свободны все» ставится по `candidateCovered`, то есть покрывает всю длительность встречи, а не только её первую клетку. Знаменатель шкалы — число отметившихся (`markedRefs.length`), тот же, что у правила кандидата: иначе при двух отметившихся из четырёх шкала физически не достигала бы максимума.

Тон дублируется в атрибутах `data-tone` (`none | partial | full | focus`), `data-free` и `data-marked`. Это не отладочный мусор, а единственный способ его проверить: jsdom не разбирает `color-mix()` и выбрасывает значение, поэтому `toHaveStyle` на таких стилях проходит при любом проценте.

Фокус на участнике — только явное наведение или тап по имени. Автоматического фокуса в админском режиме нет: он прятал тепловую карту остальных.

## Автосохранение

Правки нумеруются счётчиком `editSeq`, подтверждённый сервером номер хранится в `savedSeq`. Ответ сервера отражает состояние на момент отправки запроса, поэтому пока номера расходятся, серверные интервалы не затирают локальные, а перечитывание состояния после сохранения пропускается. Без этого клики, сделанные за время полёта запроса, откатывались назад и терялись.

## Конкурентность при назначении встречи

Проверка правила кандидата и вставка строки идут в одной транзакции, которая начинается с `select … for update` по строке `circle_schedules`. Без блокировки двое участников одного круга, нажавших «Назначить» одновременно, оба проходили проверку и создавали пересекающиеся встречи: чтение состояния и запись выполнялись разными соединениями.

`fetchCalendarPublicState` принимает соединение и флаг `skipCleanup` — внутри уже открытой транзакции уборка прошлых отметок не запускается, иначе открылась бы вложенная транзакция.

Остаточный случай: два участника **разных** кругов, назначающие пересекающиеся встречи в одну и ту же миллисекунду, блокировкой не покрыты — блокируется пространство, а не человек. Для клуба такого размера это принято сознательно.

## Высота клетки

22 px на широком экране и 26 px при ширине до 540 px — в 22 px пальцем не попасть. Порог тот же, что на доске матчинга. Геометрия проверяется в `e2e/calendar-layout.spec.ts` через `boundingBox()` вместе с отсутствием горизонтальной прокрутки.
